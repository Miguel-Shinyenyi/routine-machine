# Architecture: the concerns record

This is Routine Machine's concerns record, the table `docs/engineering-concerns.md` asks every project to keep: one row per concept, numbered 1 to 111, each answered **Applies**, **Not applicable** or **Deferred**, with a reason in one sentence and, for "Applies", the evidence (a test, a doc or a config). A claim without evidence stays "Deferred". Considered does not mean built.

**How it is being written.** Staged Prompt 7 asked for it. It is written in batches, one group of the hub document at a time, so each batch can be reviewed before the next. Every file path and line below was read in this repository on the date shown. Where I only looked for something and did not find it (for example a rate limiter), the reason says "I found none" and is not a claim that none exists anywhere.

**Status: 34 of 111 rows written.** Written: Traffic and edges; Delivery and operations; Service calls and failure; Messaging and workflows. Still to write, in the hub document's order: Real-time connections; Data access and storage; Concurrency; Scale and performance; Observability and reliability targets; Security; Change, recovery and cost; Networking and protocols; Versioning, build and infrastructure; Incidents.

## Service calls and failure

| # | Concept | Answer | Reason and evidence | Date |
|---|---------|--------|---------------------|------|
| 9 | Service discovery | Applies | Services find each other by Compose service name through environment variables: `BACKEND_URL` and `INTELLIGENCE_SERVICE_URL` for the frontend, `BACKEND_BASE_URL` for the intelligence service, `ROUTINE_MACHINE_DB_URL` for the database (`infra/docker-compose.yml:18, 73, 96, 97`). Fine for one host; it matters if services move to separate hosts. | 2026-10-26 |
| 10 | Circuit breakers | Deferred | I found no circuit breaker in any service. What exists instead is **degrading**: the Today page catches a failed call to the intelligence service and renders without it (`frontend/app/today/page.tsx:46, 54`). That limits one page's damage but does not stop repeated calls to a dead dependency. It matters when a dependency's failures would cost more than a timeout each, for example the model API at volume. | 2026-10-26 |
| 11 | Timeouts | Applies | **With one gap.** Every backend class that makes an outside call sets a timeout (10 classes: the GitHub, hub-sync, WakaTime, RescueTime and ActivityWatch clients, and the five owner-page services; for example `GitHubCommitClientImpl.java:38`, 10 s). The intelligence service uses 5 s to the backend and 30 s to the model API (`intelligence-service/main.py:188, 209, 251, 290, 350`). **The gap: the frontend's `fetch` in `frontend/lib/api.ts` has no timeout**, so a hung backend holds a page until the browser gives up. | 2026-10-26 |
| 12 | Retries | Applies | Only two, both single and deliberate. GitHub calls retry once, after 5 s, **only when the connection itself failed**; anything GitHub answered, a rate limit included, is returned at once because retrying would waste the quota (`GitHubRequests.sendWithOneRetry`, `GitHubRequests.java:46-59`; test `GitHubSendTest`). The owner page's service probe retries once after 1 s (`ServiceHealthService`; test `WatchtowerProbeRetryTest`). Everything else (WakaTime, RescueTime, ActivityWatch, the model API) fails at once and is tried again by the next scheduled run or by the person. | 2026-10-26 |
| 13 | Exponential backoff | Not applicable | The only retries are one extra try with a fixed pause (see 12), so there is no loop whose waits could grow or need jitter. It matters if a retry count above one is ever added. | 2026-10-26 |
| 14 | Idempotency | Applies | **Through the database, not a request key.** A repeated action cannot make a second row where it would be wrong: `UNIQUE (user_id, source, source_event_id)` on evidence events and `UNIQUE (user_id, goal_id, local_date)` on daily credits (`V19__evidence_to_credit_pipeline.sql`), `UNIQUE (user_id, local_date)` on savings so tapping twice is one saving (`V22__granary.sql`, `docs/backend.md:471`), unique goal names per person (`V16__goal_user_scoping.sql`), one answer per person per week (`V31`; test `answeringAgainInTheSameWeekChangesTheAnswerAndKeepsOneRow`), one demo account (test `openingTheDemoAgainReusesTheAccountAndAddsNoRows`). **There is no `Idempotency-Key` header**, so a double-submitted form that has no such unique rule, for example a pause, can still be recorded twice. | 2026-10-26 |
| 44 | Backpressure | Not applicable | Every request is handled where it arrives, with no queue or stream between a producer and a consumer, so nothing can pile up unseen; the only background work is the scheduled syncs, run one after another. Limiting the volume of incoming requests is row 1. | 2026-10-26 |

## Messaging and workflows

| # | Concept | Answer | Reason and evidence | Date |
|---|---------|--------|---------------------|------|
| 15 | Message queues | Not applicable | There is no queue: no messaging library in the dependency files of the backend, the frontend or the intelligence service, and no queue code in the backend source (the frontend's own "queue" is a short cookie that carries analytics notes from the server to the browser, `frontend/lib/analytics/queue.ts`, not a work queue). No service hands work to another to be done later. Calls are request and answer. It matters if work is ever moved off the request, for example slow model calls. | 2026-10-26 |
| 16 | Pub/sub | Not applicable | Nothing publishes to subscribers. The one outgoing stream of events is product analytics, which goes from a visitor's browser to one receiver (the owner's PostHog project), only after consent, and only for names on an allow-list (`frontend/lib/analytics/events.ts`, `docs/frontend.md`, "Analytics"). | 2026-10-26 |
| 17 | Event-driven architecture | Not applicable | The application changes state through ordinary request and answer writes. `evidence_events` is a table of evidence records that credits are worked out from (`docs/backend.md`, Phase 9), not a bus others react to, so there is no replay or ordering of events to guard. | 2026-10-26 |
| 18 | Distributed transactions | Not applicable | Each action changes one database in one transaction. No action must change two systems together: the intelligence service and PostHog are never written as part of the same action. The closest case, a reading note that is saved and then assessed, is built so the two do not need to succeed together (see 19). | 2026-10-26 |
| 19 | Saga pattern | Not applicable | There is no multi-step workflow across systems whose half-failure needs undoing. The reading note is designed so a failed assessment leaves the saved note in place: "writing the note down is the user's actual action, assessment is an addition to it, not a precondition for it" (`backend/.../domain/ReadingNote.java:21-24`). | 2026-10-26 |
| 20 | Dead letter queues | Not applicable | There is no queue to dead-letter from (see 15). The nearest thing is a sync that keeps failing: it is counted (`sync_consecutive_failures`), raises the `SyncSourceFailing` alert after three failures in a row (`infra/observability/alerts.yml:28`) and shows on the owner's `/watchtower` page, which is where someone looks. | 2026-10-26 |
| 21 | Cron jobs | Applies | **Five scheduled jobs**, the WakaTime, ActivityWatch, GitHub, hub and RescueTime syncs, each `@Scheduled(fixedDelay...)` every 15 minutes by default (for example `GitHubSyncService.java:64`). `fixedDelay` waits until a run has finished before counting the interval, so a job cannot overlap itself in one instance. **Running twice is safe**: syncing the same day twice updates the measurement and creates no second daily log (tests `syncingTheSameDayTwiceUpdatesTheMeasurementInsteadOfDuplicatingIt` and `syncingTheSameDayTwiceDoesNotCreateASecondDailyLogForTheRoutineItem` in `GitHubSyncServiceTest` and `WakaTimeSyncServiceTest`). **A missed run is caught up**: the WakaTime and ActivityWatch syncs look back over 7 days (`docs/backend.md:195`). **Gaps**: there is no lock, so two backend instances would each run every job and double the GitHub quota (`docs/hub-sync.md`); and I found no alert for a sync that stops running without failing, because the alert counts failures only. | 2026-10-26 |
