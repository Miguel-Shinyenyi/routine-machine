# Architecture: the concerns record

This is Routine Machine's concerns record, the table `docs/engineering-concerns.md` asks every project to keep: one row per concept, numbered 1 to 111, each answered **Applies**, **Not applicable** or **Deferred**, with a reason in one sentence and, for "Applies", the evidence (a test, a doc or a config). A claim without evidence stays "Deferred". Considered does not mean built.

**How it is being written.** Staged Prompt 7 asked for it. It is written in batches, one group of the hub document at a time, so each batch can be reviewed before the next. Every file path and line below was read in this repository on the date shown. Where I only looked for something and did not find it (for example a rate limiter), the reason says "I found none" and is not a claim that none exists anywhere.

**Status: 20 of 111 rows written.** Written: Traffic and edges; Delivery and operations. | 3 | Load balancing | Not applicable | Each service runs as one container (`infra/docker-compose.yml` has no replicas), so there is no choice of instance to make. It matters if a service is ever run twice (see 45 and 46). | 2026-10-26 |
| 4 | Reverse proxies | Deferred | No reverse proxy is in the compose file, and production hosting is not decided (`PROJECT.md`, Backlog G, the "Later" list). | 5 | API gateways | Not applicable | There is one backend, and it checks the signed token itself on every route (`SecurityConfig` and `EveryRouteNeedsATokenTest`); the frontend's server is its caller and routing is by URL path. | 48 | CDN | Deferred | No static assets are served at a scale or distance where it matters, and public hosting is not decided. It matters when the app is hosted for people far from the host. | 2026-10-26 |
| 49 | Edge caching | Deferred | Goes with 48. Pages are personal (signed-in data), so only static assets could ever be cached at an edge, and never a page. | 2026-10-26 |
| 50 | Cache invalidation | Applies | The one cache (see 2) has no invalidation except a service restart, and that is safe: an analogy is reproducible from its inputs alone, so a stale or lost entry costs one model call (`intelligence-service/main.py:154-157` says so). It grows with the number of different (topic, interest) pairs and is never trimmed, which is the memory question in 41. | 2026-10-26 |

## Delivery and operations

| # | Concept | Answer | Reason and evidence | Date |
|---|---------|--------|---------------------|------|
| 6 | CI/CD | Applies | **CI is built, CD is not.** `.github/workflows/ci.yml` runs the backend tests (Testcontainers), `pytest` and the frontend lint, tests and build on every pull request and every push to `main`; it was green on PR #9 (`PROJECT.md`, status log, 2026-10-26). Nothing deploys anywhere yet: hosting and deployment automation are the "Later" list (`PROJECT.md`, Backlog G). | 2026-10-26 |
| 7 | Docker | Applies | Each service has a Dockerfile; backend and frontend are multi-stage with small runtime images (`eclipse-temurin:21-jre-alpine`, `node:20-alpine` with Next's standalone output). A fresh clone built all of them and passed every suite (`PROJECT.md`, status log, 2026-10-25, "part 7: the fresh-clone run"). Base images are pinned by version tag, not by digest. | 2026-10-26 |
| 8 | Kubernetes | Deferred | Nothing runs on Kubernetes; the stack is Docker Compose (`infra/docker-compose.yml`) and Kubernetes is on the "Later" list (`PROJECT.md`, Backlog G). It matters the day a Kubernetes host is chosen, when limits, probes and rollout rules need writing (see 56 and 57). | 2026-10-26 |
| 51 | Feature flags | Applies | Optional features are environment switches, off unless set: `DEMO_PROFILE_ENABLED` (tests `DemoLoginDisabledApiIntegrationTest`), `RESCUETIME_SYNC_ENABLED`, `POSTHOG_KEY` and `POSTHOG_HOST` (no banner and no library when unset, tested in `frontend/lib/analytics/consent.test.ts`), `TRACING_ENABLED`. All are in `infra/docker-compose.yml`, and all but `TRACING_ENABLED` are named in `infra/.env.example` (a small gap: that one is missing there). **A change needs the container recreated; there is no flag service that changes at run time.** | 2026-10-26 |
| 52 | Blue-green deployment | Deferred | There is one stack, and `docker compose up` replaces a container, so the old version does not keep running. It matters at the first deployment with real users. | 2026-10-26 |
| 53 | Canary releases | Deferred | Goes with 52: nothing splits traffic. It matters once there is traffic worth splitting. | 2026-10-26 |
| 54 | Rolling deployments | Deferred | I found no graceful-shutdown setting in the backend configuration, and each restart during this work was a short outage (nothing answered until the container was back). It matters at the first deployment, when requests in flight at a restart become someone's lost action. | 2026-10-26 |
| 55 | Rollbacks | Applies | **Documented, not rehearsed.** The application returns to a good version by reverting the commit and rebuilding the image; every status row in `PROJECT.md` ends in an "Undo:" line. Database migrations are forward-only (`docs/database.md`, V29), and the recent ones (V30 to V32) only add a column or a table and say how to drop them (`docs/database.md`). I have not rolled a version back against real data. | 2026-10-26 |
| 56 | Health checks | Applies | **With one gap.** The backend serves `/actuator/health` on its own management port 8081, details hidden (`docs/observability.md:36-40`); the intelligence service has `GET /health`; Prometheus reads both as `up`, and the owner's `/watchtower` page lists every service's state (`ServiceHealthService`, `docs/observability.md`, "Piece 1"). "Healthy" means the process answers; it does not test the database or the model key. The gap: the compose file has no `healthcheck:` entries. | 2026-10-26 |
| 57 | Liveness and readiness probes | Deferred | Each service has one health endpoint that serves as both. Compose defines no probes and `depends_on` waits only for a container to start, not to be ready (`infra/docker-compose.yml`). It matters when an orchestrator or a host needs separate "alive" and "ready" answers. | 2026-10-26 |
| 58 | Monitoring | Applies | Prometheus, Alertmanager and Grafana (compose profile `observability`) with four alert rules (`infra/observability/alerts.yml`: `BackendDown`, `IntelligenceServiceDown`, `SyncSourceFailing`, `AssessmentFailureRateHigh`), unit-tested with `promtool` (`infra/observability/alerts_test.yml`) and one fired live on 25 Oct 2026 (`docs/observability.md:407`). **No notification channel is connected**: a firing alert is visible only in Prometheus and Alertmanager's own pages. | 2026-10-26 |
| 59 | Logging | Applies | One request id is on the response and on every log line of the request, across the frontend, backend and intelligence service; logs are one JSON object per line with a fixed list of fields, so a careless `extra=` cannot leak (`backend/.../RequestIdFilter.java` with `RequestIdFilterTest`; `intelligence-service/observability.py` with `test_observability.py:19, 25, 41, 53`). A test refuses the text of a note or the book title in any log line or metric (`test_no_metric_or_log_line_carries_the_note_text`). Loki holds the logs for the owner's page. | 2026-10-26 |
